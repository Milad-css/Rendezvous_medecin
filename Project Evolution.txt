  [1.3] LES MIGRATIONS — C'EST QUOI ?
  ─────────────────────────────────────
  Une migration est un fichier PHP qui décrit la structure d'une table
  de la base de données. Elle permet de créer les tables automatiquement
  sans écrire du SQL à la main.

  Créer un fichier de migration :
  ─────────────────────────────────
  php artisan make:migration create_patients_table

  Exemple de migration pour la table patients :
  ───────────────────────────────────────────────
  public function up(): void
  {
      Schema::create('patients', function (Blueprint $table) {
          $table->id();                                          // Clé primaire auto-incrémentée
          $table->foreignId('user_id')->constrained()           // Clé étrangère → table users
                                      ->onDelete('cascade');    // Suppression en cascade
          $table->string('telephone');                          // Colonne texte
          $table->timestamps();                                 // created_at + updated_at
      });
  }

  Commandes utiles :
  ───────────────────
  php artisan migrate              → Exécute toutes les migrations (crée les tables)
  php artisan migrate:fresh        → Supprime toutes les tables et les recrée
  php artisan migrate:rollback     → Annule la dernière migration


  [1.4] AUTHENTIFICATION AVEC LARAVEL SANCTUM
  ─────────────────────────────────────────────
  Sanctum génère un TOKEN unique par utilisateur à chaque connexion.
  Ce token est ensuite envoyé par React dans chaque requête pour
  prouver que l'utilisateur est bien authentifié.

  Générer un token :
  ───────────────────
  $token = $user->createToken('auth_token')->plainTextToken;

  Pourquoi ne pas vérifier le mot de passe dans React ?
  ──────────────────────────────────────────────────────
  On ne compare JAMAIS le mot de passe côté frontend, car cela
  obligerait à envoyer le mot de passe haché au client → faille de sécurité.
  La vérification se fait exclusivement dans le contrôleur Laravel
  avec Auth::attempt(), qui compare le mot de passe reçu avec le hash en base.

  Contrôleur Auth — login() :
  ─────────────────────────────
  if (!Auth::attempt(['email' => $request->email, 'password' => $request->password])) {
      return response()->json(['message' => "Email ou mot de passe incorrect"], 401);
      // 401 = Non autorisé → Axios dans React recevra ce code dans le catch()
  }
  $user  = Auth::user();
  $token = $user->createToken('auth_token')->plainTextToken;
  return response()->json(['user' => $user, 'token' => $token]);

  [2.1] LOGIN ET REGISTER — LOGIQUE COMPLÈTE
  ───────────────────────────────────────────
  Étapes dans les composants Login.jsx / Register.jsx :
    1. Utiliser useState pour gérer les champs du formulaire
    2. Valider les champs (email valide, mot de passe non vide...)
    3. Envoyer les données avec api.post() vers Laravel
    4. En cas de succès → dispatch(setCredentials()) pour remplir Redux
    5. Rediriger vers le dashboard avec navigate()
    6. En cas d'erreur 401 → afficher le message d'erreur à l'utilisateur

  Exemple — Traitement de la réponse login dans React :
  ──────────────────────────────────────────────────────
  api.post('/login', formData)
      .then((res) => {
          dispatch(setCredentials({
              user:  res.data.user,
              token: res.data.token,
          }))
          setFormData({ email: '', password: '' })
          setErrors([])
          navigate('/dashboard')   // Redirection après connexion réussie
      })
      .catch(() => {
          newErrors.push('Email ou mot de passe incorrect')
          // Laravel a renvoyé 401 → Axios déclenche le catch()
      })


  [2.2] DASHBOARD PATIENT — FONCTIONS PRINCIPALES
  ─────────────────────────────────────────────────

  Prendre un rendez-vous :
  ─────────────────────────
    → Vérifier que l'utilisateur a sélectionné un service ET un créneau
    → api.post('/rendezvous/prendre', { service_id, creneau_id })
    → Après succès : rafraîchir la liste des RDV + la liste des créneaux

  Annuler un rendez-vous :
  ─────────────────────────
    → api.delete('/rendezvous/' + id)
    → Laravel supprime le RDV ET remet le créneau disponible (disponible = true)
    → Après succès : rafraîchir la liste des RDV + la liste des créneaux

  Afficher mes rendez-vous :
  ───────────────────────────
    → api.get('/rendezvous/mes') → reçoit les RDV du patient connecté
    → Afficher chaque RDV avec : service, date, heure, statut
    → Ajouter un bouton "Annuler" devant chaque RDV

  Déconnexion (Logout) :
  ───────────────────────
    → dispatch(logout())            → vide le store Redux (efface token + user)
    → api.post('/logout')           → Laravel détruit le token en base
    → navigate('/login')            → redirige vers la page de connexion

  [3.1] CONCEPT
  ──────────────
  FullCalendar est une bibliothèque React qui affiche un calendrier
  interactif. On lui passe une liste d'événements (créneaux) et il
  les affiche sur la grille de façon visuelle.

  Pense au calendrier comme une fenêtre :
    → Tu choisis CE QUE l'utilisateur voit (mois, semaine, jour)
      via la prop initialView
    → Tu choisis LES BOUTONS disponibles via headerToolbar

  Vues disponibles :
  ───────────────────
    dayGridMonth   → Vue mensuelle classique (grille de mois)
    timeGridWeek   → Vue hebdomadaire avec les heures (emploi du temps)
    timeGridDay    → Vue journalière avec les heures

  [3.2] EXEMPLE D'UTILISATION
  ─────────────────────────────
  <FullCalendar
    initialView="dayGridMonth"
    locale="fr"
    headerToolbar={{
      left:   'prev,next today',           // Boutons navigation (gauche)
      center: 'title',                     // Titre du mois/semaine (centre)
      right:  'dayGridMonth,timeGridWeek'  // Boutons de changement de vue (droite)
    }}
    events={creneaux.map(c => ({           // Convertir les créneaux en événements
      title: c.disponible ? 'Disponible' : 'Réservé',
      date:  c.date,
      color: c.disponible ? '#40916C' : '#E74C3C'
    }))}
  />

  Installation :
  ───────────────
  npm install @fullcalendar/react @fullcalendar/daygrid @fullcalendar/timegrid

  BUGS RENCONTRÉS ET SOLUTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  BUG 1 — Problème CORS
  ──────────────────────
  Symptôme : Le navigateur bloque les requêtes de React (port 5173)
             vers Laravel (port 8000)
  Cause     : Le navigateur interdit les appels cross-origin par défaut
  Solution  : Configurer config/cors.php dans Laravel pour autoriser
              l'origine http://localhost:5173

  BUG 2 — Créneau non remis disponible après annulation
  ───────────────────────────────────────────────────────
  Symptôme : Après annulation d'un RDV, le créneau restait "indisponible"
  Cause     : La méthode annuler() supprimait le RDV mais oubliait de
              remettre le créneau à disponible = true
  Solution  : Ajouter après la suppression du RDV :
              $creneau->update(['disponible' => true]);

  BUG 3 — Store Redux réinitialisé au rechargement de page
  ──────────────────────────────────────────────────────────
  Symptôme : L'utilisateur était déconnecté à chaque rechargement
  Cause     : Redux est en mémoire — il se réinitialise au refresh
  Solution  : Synchroniser le store avec localStorage :
              sauvegarder le token au login, le relire au démarrage

  BUG 4 — Routes accessibles sans authentification
  ──────────────────────────────────────────────────
  Symptôme : Un patient pouvait accéder à /dashboard/medecin en tapant
             l'URL directement dans le navigateur
  Cause     : Pas de protection des routes côté frontend
  Solution  : Créer le composant ProtectedRoutes qui vérifie le rôle
              dans le store Redux avant de rendre la page
